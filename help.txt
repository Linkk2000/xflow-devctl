AI call recipes:
  Human Approval Is Non-Delegable. AI may prepare approval files, evidence,
  command drafts, and review notes, but AI must never satisfy a human gate itself.

  Task-scoped unattended mode:
    devctl unattended enable --issue <id|draft> --confirm XFLOW_HUMAN_UNATTENDED_ALL
    devctl unattended status
    devctl unattended disable

  State is stored only in .xflow/local/unattended.json without the safety word
  or tokens. It is bound to the Git common directory, worktree, and current
  task Issue. Mismatch is invalid and fails closed without state repair. Draft
  migrates only after a provider returns a definite Issue ID. A current-task
  Issue mismatch, S10_DONE, successful Issue close, successful task start,
  successful human-approved git done, or unattended disable invalidates it permanently.

  Unattended mode bypasses only the local human approval file. Current-task,
  draft, dependency, evidence, attachment, sensitive-data, provider, platform,
  test, and completion checks remain mandatory. Each actual bypass prints:
    [UNATTENDED] Human approval gate bypassed for current task <id>.

  --no-local-review alone is invalid. It is only a compatibility flag when an
  already-valid matching state exists. The mode does not authorize force push,
  history rewrite, destructive deletion, secret or permission changes, or any
  expansion of existing --force behavior.
  Unattended mode never authorizes local branch deletion. git done requires
  exact human approval action git-cleanup; --force requires git-cleanup-force.

  task-state/local-review bytes, repository/worktree/base/target bindings, and
  observed remote base commit in a persistent claim. After a crash, rerun that
  same git start command. Replay resumes only the exact claimed branch/start
  point and fails closed on missing or conflicting identity; it does not create
  a new approval or bypass human approval.

Core remote-write rule:
  Remote writes require local human review of the exact body/evidence file or
  a matching task-scoped unattended state.
  Human Approval Is Non-Delegable: AI must never satisfy a human gate itself
  and must never edit Approved: no to Approved: yes.
  Use --body-file for issue create/comment and git mr.
  Active approval file: .xflow/issues/issue-<id>/approvals/local-review.md
  Issue/comment image attachments are disabled.
  Inline --attach-file and --upload-attachments are disabled for issue create/comment.
  Push and MR are separate gates: devctl git push --issue <id> only publishes the
  current branch, while devctl git mr only creates the PR/MR after the branch
  already has an upstream and no unpushed commits.
  After PR/MR creation, devctl writes a state backfill commit containing XFlow
  PR number/URL state and pushes that metadata-only commit to the same branch.

Problem/Gap Closure Loop:
  Oral problem/gap reports become .xflow/issues/issue-draft/gap-analysis.md
  or .xflow/issues/issue-<id>/gap-analysis.md before implementation.
  The gap analysis must include local evidence, scope, proposed changes,
  acceptance criteria, human recognition, and one evidence bundle per finding.
  Each bundle records observation, direct local artifact, analysis, acceptance,
  and a human-review checkbox. UI bundles require evidence/screenshots and
  evidence/dom artifacts; all issue-level evidence stays under evidence/.
  After implementation, write .xflow/issues/issue-<id>/resolution-report.md
  with local evidence, one fresh verification bundle per criterion, and a
  resolved|reduced|blocked conclusion. A code diff or "tests passed" claim is
  not completion evidence.
  For resolved/reduced, all AI self-review checklist items must be checked.
  If the report is not true, AI must rework and rewrite it before handoff.
  devctl check gap-analysis --issue <id>
  devctl approval prepare --issue <id> --action gap-recognition --file .xflow/issues/issue-<id>/gap-analysis.md
  devctl gap recognize --issue <id> --file .xflow/issues/issue-<id>/gap-analysis.md
  Recognized: yes is reviewed content, not authorization. Only the immutable,
  non-reusable human gap-recognition record authorizes implementation-gap.
  Contract acceptance and unattended mode cannot satisfy this gate.
  devctl check resolution-report --issue <id>

Approval:
  devctl approval prepare --issue draft|<id> --action ACTION --file F [--attachments manifest.json] [--command CMD] [--reviewer NAME] [--force]
  devctl approval reconcile --issue <id|draft> --approval-id <id> --outcome no-effect|success --confirm XFLOW_HUMAN_REMOTE_RECONCILED [--target-issue <id>] [--provider-receipt <JSON-object>]
  devctl approval supersede-branch-start --issue <id> --approval-id <id> --reason "<auditable reason>" --confirm XFLOW_HUMAN_SUPERSEDE_TASK_BRANCH_START
  reviewer defaults to git config user.name/user.email when available
  Prepared by AI or tooling does not mean approved.
  Only the human reviewer may change Approved: no to Approved: yes.
  Reconcile only after a human checks authoritative remote state. no-effect makes
  the one-use approval retryable; success seals the supplied remote receipt and
  completes locally without another provider call.

Task authority v2 and contract closure:
  Run these commands from the repository worktree that owns the task. Portable
  examples use devctl; in native Windows PowerShell, replace each leading
  devctl with .\devctl.ps1. Do not use a user-level PATH devctl shim.

  Task authority is repository-common but worktree-bound. In parallel worktrees,
  activate and inspect the task from the worktree that owns the branch:
    devctl task activate --issue IK3RR6
    devctl task status
    devctl task list
  task status reports the repository, worktree, branch, Issue, execution state,
  semantic phase, classification, and selected contract. Parallel worktrees do
  not share an active task identity just because they share one Git repository.

  The shortest happy path for a contract-bearing Issue is:
    devctl task activate --issue IK3RR6
    devctl check classification --issue IK3RR6
    devctl contract lint --file docs/requirements/composed-activity/contract.yaml
    devctl approval prepare --issue IK3RR6 --action contract-acceptance --file docs/requirements/composed-activity/contract.yaml --objects <approved-id-list>
    devctl contract accept --issue IK3RR6 --file docs/requirements/composed-activity/contract.yaml --objects <approved-id-list>
    devctl trace check --issue IK3RR6 --matrix .xflow/issues/issue-IK3RR6/traceability-matrix.yaml
  Native Windows PowerShell recipe:
    .\devctl.ps1 task activate --issue IK3RR6
    .\devctl.ps1 check classification --issue IK3RR6
    .\devctl.ps1 contract lint --file docs/requirements/composed-activity/contract.yaml
    .\devctl.ps1 approval prepare --issue IK3RR6 --action contract-acceptance --file docs/requirements/composed-activity/contract.yaml --objects <approved-id-list>
    .\devctl.ps1 contract accept --issue IK3RR6 --file docs/requirements/composed-activity/contract.yaml --objects <approved-id-list>
    .\devctl.ps1 trace check --issue IK3RR6 --matrix .xflow/issues/issue-IK3RR6/traceability-matrix.yaml

  Mechanical contract commands:
    devctl check classification --issue IK3RR6 [--file .xflow/issues/issue-IK3RR6/classification.yaml]
    devctl contract lint --file docs/requirements/example/contract.yaml
    devctl contract diff --old <old.yaml> --new <new.yaml>
    devctl trace check --issue IK3RR6 --contract <contract.yaml> --matrix <traceability-matrix.yaml>
    devctl trace check --issue IK3RR6 --matrix <traceability-matrix.yaml>
  Omit --contract when immutable sealed contract-acceptance history is the authority.
  An explicit --contract is non-authoritative mechanical fail-closed evolution input.
  It cannot replace sealed acceptance or create acceptance authority.
  Non-acceptance routes still require --contract.
  Classification, lint, diff, and trace check are mechanical validation and
  comparison steps. lint does not approve semantic quality. A passing lint,
  diff, or trace check is evidence for review, never a human acceptance.

  Contract acceptance is a human-only command boundary:
    devctl approval prepare --issue IK3RR6 --action contract-acceptance --file docs/requirements/example/contract.yaml --objects <id,id,...>
    devctl contract accept --issue IK3RR6 --file docs/requirements/example/contract.yaml --objects <id,id,...>
  The human reviewer must review the exact file and approved object list, then
  change the prepared review from Approved: no to Approved: yes. AI may prepare
  the review and run mechanical checks, but may not approve or accept on the
  human's behalf. contract acceptance never supports unattended mode.
  A successful acceptance seals immutable approval history under
  .xflow/issues/issue-<id>/approvals/history/; do not edit, reuse, or manually
  manufacture approval history records.

  The normal user and AI interface is devctl task status. devctl hook task-status
  is an internal integration hook for an already-authorized inherited mutation
  lease; it is not a normal workflow entrypoint. Do not use `devctl hook task-status` as a normal user or AI command.

Task and issue-workspace migration:
  Existing repositories with only .xflow/current-task.md can migrate once from
  the owning worktree:
    devctl task migrate-current
  Keep the legacy file only while compatibility consumers still need it; the v2
  task authority becomes the source of truth after migration.

  .xflow/issues/ is tracked by default. Inspect before changing an older local
  workspace policy, then apply the selected mode only after a human reviews the
  reported ignores, active approvals, credentials, local paths, and large files:
    devctl migrate issue-workspace --mode tracked --check
    devctl migrate issue-workspace --mode tracked --apply
    devctl migrate issue-workspace --mode local --check
    devctl migrate issue-workspace --mode local --apply
  tracked keeps Issue evidence and approval history in Git. local is a legacy
  exception for repositories that intentionally ignore .xflow/issues/; it is
  not the default and may require manual remediation before apply.

    python tests/python-core.py
    python tests/entrypoint-routing.py
